# Uagray 设计检查

## 依据与范围

仓库根目录为本文件所在目录的 `../../..`。先读取 [设计参考规范](../../../docs/design-system.md) 的相关章节；API 与 Token 接入分别查对应工程文档。历史研究不覆盖现行规则，待讨论项不作为违规依据。

若 Skill 被复制到其他位置，定位实际 Uagray 仓库再执行脚本。检查其他宿主项目时，库的源码检查不能替代宿主组合检查；明确本次真正检查的文件和状态，不以库脚本通过证明任意页面已经符合规范。

## 定向核查

1. 根据用户范围和 git diff 确认涉及的组件、CSS、Motion、宿主组合与状态。检查完整任务单元，区分规则缺口、明确违反规则、合法例外和仅需视觉验证的疑点。
2. 在库根目录执行 `npm run check:design -- --json`。结果包含通过的登记契约、带文件行号的问题与能力边界。脚本检查显式基础声明及已登记的几何组合，不计算完整 CSS 级联、媒体查询、DOM 布局、宿主覆盖或实际色差。
3. 对涉及圆角的组合检查外/内轮廓、真实 padding 和必要边缘；不要只核对两个 Token 名称。检查 CSS 与 Motion 是否读取同一变量、同尺寸图标与文字按钮是否一致、同排控件的外高是否对齐。新组合若未登记，补可计算的关系后才能给出静态证据。
4. 根据任务核查环境与边界归属、内容/控件宽度、组内/组间可见距离、状态前景、文字重量、原生语义与焦点。明确装饰渐隐是否对应真实隐藏内容、是否遮挡必要操作，动效是否即时响应与支持减少动态效果。
5. 仅评审时报告问题；用户已要求修复时落实范围内的问题并运行相关类型/交互检查。修改检查器则用 `npm run test:design` 验证它能发现真实几何回归，不能通过降低标准、跳过缺失声明或增加 blanket ignore 抹平失败。

## 证据与停止条件

- 问题必须给出实际文件/行号、违反的主规范章节、触发场景与建议，避免仅说“不统一”或机械罗列全部原则。
- 脚本可证实的偏差与需实际呈现确认的疑点分别说明；条件表达式或复杂覆盖无法证明时直接说明，不推导成通过。
- CSS 数值对齐不证明光学对齐，源码状态不证明浏览器焦点或动效。浏览器与大规模兜底验证需先获用户同意；未获同意时完成可做的定向检查并如实说明边界。
- 不擅自改变已确认方向、不修改上游 SVG、不扩展业务流程或执行发布。主规范仍有待讨论细节时，提出针对具体场景的选择，不把某次实现提升为系统规则。
