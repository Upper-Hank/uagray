## 定位与原则

Uagray 是可供其他 React 项目使用的轻量设计系统。最初从 anish’s lab 学习灰阶气质与部分设计细节，此后依据自己的规则独立设计。色值、尺寸、组件清单与页面编排都可以演进；保留一致的层次、留白、柔和表面与克制反馈。

架构要支持复用，同时控制维护成本：一个包、一个仓库、少量语义 token、原生 CSS 与必要的交互逻辑。先面向现有 React 使用场景，不承诺跨框架、完整主题引擎或复杂组件覆盖。

## 规范与实现的分层

依据 [视觉准则 v0.1](visual-language.md) 组织四层规范：Foundation 管理资源；Visual Patterns 记录 Tonal/Defined/Physical 等重复处理；Component Specifications 定义合法外观与行为；Composition Guidelines 定义 Form/Table/Workspace 等组织关系。后两层的具体契约保存在 design-system.md 与 api-contract.md。

规范层次不等于四个代码包或 Token 层。仅当处理方式具有稳定复用价值时才提取共享实现。环境可提供色值，不能仅因背景变化替组件决定对象边界、抬升或交互语义。本轮将环境资源与边界处理分开，取消 action-shadow 及状态/进度/选择/Switch 的祖先自动映射；Surface treatment 定义合法的重复处理，不新增独立代码包。源码与定向测试已覆盖，浏览器视觉尚未验收，见 visual-polish.md。

## 建议的最小架构

```text
src/ui/
  index.ts                 公共导出
  tokens.css               语义变量；不捆绑站点资源路径
  components.css           组件样式；限定作用域
  icons.tsx                Uplus Icon 适配
  button.tsx               按实际维护边界拆分组件文件
  segmented-control.tsx
  ...
src/App.tsx                展示与用法示例
src/app.css                站点重置与展示样式
public/fonts/              展示站字体；库的字体接入需单独约定
vite.lib.config.ts         库构建，与展示页构建分离
tsconfig.lib.json         类型声明输出（文件名以实现为准）
docs/                      规范、API 与变更说明
```

组件文件分拆只为维护清晰，不引入每组件目录模板或多包工作区。可按实际增长调整。

预期消费接口（尚未实现）：

```tsx
import { Button, Surface } from "uagray";
import "uagray/styles.css";
```

推荐 ESM 库输出并生成 `.d.ts`，React 作为 peer dependency 且不打入库产物；CSS 显式导入，保留 CSS 副作用；字体默认可用系统回退，品牌字体由独立入口或宿主配置接入。Vite 原生库模式足以支持这个规模，不需要额外重型打包方案。[Vite 库模式](https://vite.dev/guide/build.html#library-mode)、[npm 包字段规范](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/)。实际配置必须匹配项目安装的 Vite 7，不直接套用新版文档的所有字段。

## 推荐实施顺序

1. **复用底座**：库产物、类型与 CSS 入口、React 边界、字体与样式隔离，以及 PageShell/原生属性契约。同步更新示例。
2. **最小消费闭环**：从本地打包产物安装到一个小型 React 消费例子，验证真实接入。
3. **表单基础**：Field、Input、Textarea，再补 Checkbox、Radio、Switch；优先状态与可访问关联的一致性。
4. **需求驱动扩展**：Select、Tabs 和反馈组件，真实项目需要浮层时再评估实现。

基础表单与需求驱动扩展已按本轮授权先行完成。复用底座和真实包消费仍是下一批架构工作，不因组件增多便视为可直接发布。

## 轻量性的验收要求

- 通过公共包入口使用，不复制组件源码或修改宿主路由。
- 引入组件样式不会改变宿主页面中无关元素的盒模型、字体或动效。
- 无需复制 `/fonts` 到宿主根目录即可使用基础组件。
- 单个控件不带入整套图标、展示站或第二份 React。
- 常用状态能直接表达，避免不断增加仅服务展示页的 props。
- 保持 Uagray 的视觉一致性；组件可以超出参考站，也可以必要时重新设计。

## 与用户协商的架构安排

当前运作：设计规则指导 CSS token；token 供组件样式消费；React 组件承担语义、属性和交互；展示站维护示例数据、筛选与路由。其他项目目前需导入源码，独立安装包入口尚未实现。展示站采用左目录、右实践，实践区使用真实组件；Token 目录读取实际 CSS 值。

建议先讨论以下三项，再实施下一批架构调整：

| 决策       | 建议                                             | 另一种取舍                                     |
| ---------- | ------------------------------------------------ | ---------------------------------------------- |
| 使用方式   | 单个 npm 包，统一维护                            | 按项目复制源码，便于局部修改，但更难同步修复   |
| 视觉自由度 | 保持 Uagray 默认气质，开放有限语义 token         | 自由重设全部视觉，扩大适配与维护成本           |
| 库的边界   | 基础控件与组合组件为核心，PageShell 属于可选布局 | 同时规定业务页面骨架，接入更快但对宿主约束更多 |

这些建议尚未作为用户决定落实。用户希望参与架构安排；不要凭路线图自行执行下一轮重构。
