# 组件问题与原则漏洞：第二轮讨论

依据：用户提供的六张截图、其对参考卡片 hover 的描述，以及当前项目源码。仅分析和记录，未修改组件、Token 或页面；未使用浏览器，未运行测试。尚未决定的处理保持为讨论项。

## 1. Hover 出现的卡片标题与白色操作外观

用户事实：参考作品卡片 hover 时背景不变，左下角出现灰色胶囊标题。当前卡片出现白色、浅边缘/阴影的提示，并附外链图标。

代码事实：components.css 的 ui-showcase-caption 固定消费 raised 与 shadow；仅在 hover/focus 出现（小屏常驻）。卡片自身没有 hover 改背景规则。因此，“背景不变、局部出现”已有实现基础，偏差主要是出现的内容被赋予了白色分离表面和操作外观。

根因：把“独立显示的一块内容”直接归到独立白色层，未先区分内容是卡片注释、归属标识、独立工具还是操作。标题依附于整个卡片，却得到接近独立按钮的边界和图标表达。

分类：规则缺项与具体选型失误共同存在。R1/R3/R4 要求说明用途，但没有提供足以判断标题提示的职责分类；不能仅说执行者没有使用正确颜色。

待补原则：内容的出现方式与表面样式分别定义。hover 出现不自动等于浮层，独立形状也不自动等于独立操作。局部灰色胶囊在灰卡片上可以是必要的信息注释，不应被“禁止灰色嵌套”的过度概括排除。

## 2. 工作台工具栏中的 Slider

代码事实：cases.tsx 将标准 Slider 直接放进横向 case-toolbar。Slider 要求 label，并始终生成标签/数值行和 range；CSS 为 grid、14px gap，range 高度 4px、上下 margin。案例只指定宽度 160px，未改变其字段结构。相邻按钮高度为 36px，工具栏 align-items:center 只能对齐完整组件的中心，不能使内部轨道与动作成为一个操作行。

根因：把带字段展示的整体 Slider 当作可直接组合的轨道本体。工具栏只知道排列子元素，无法改变其内部信息结构。

分类：已确认原则未落实，同时存在组件契约缺口。R7 的尺寸协调、R9 的单件与可选标签已经提出，但没有落实到组件拆分及消费方案。即便规范存在，示例仍使用旧接口；应标注“未实施”，不能称已按新规范建设。

待补原则：分别规划控件本体、字段组合、工具栏组合。排版组合应明确操作轴、总高度、必要标签/数值的安放与窄宽处理；不能把 flex 居中当作组合设计完成，也不能通过缩字号掩盖错误结构。

## 3. 按钮文字与图标均显重

代码事实：font-weight-button 当前统一 500，所有 plain/soft 等按钮主文字消费。图标默认 weight=1.5、absoluteWeight=true；Button 将图标大小固定为 15。上游 absoluteWeight 会按 24/size 补偿描边缩放。因此图标变小后，笔画不会按图形大小同步变细，1.5 这个数值不能保证小图标看起来轻。

根因：一是对具体文字偏细的反馈采取了整个 Button 类统一 500 的推广，缺少组合校准；二是将统一描边参数视为统一视觉重量，忽略大小、几何复杂度、字体、前景深浅与承载背景共同影响结果。

分类：目前代码执行了现有数值规则，但数值规则和验收条件不足。不能把问题认定为忘记设置细描边，也不能从截图直接宣布另一个描边数字就是答案。

待补原则：以图标与相邻文字的视觉重量关系进行校准，文字和图标必须一起评估；同一状态不随意增重。选择语义一致的角色后再确定数值，不能一边按字体文件名，一边按笔画像素各自定标。是否保留全部按钮 500、如何使用 450、absoluteWeight 是否适合小尺寸，仍需讨论，暂未修改。

## 4. SaaS 批量操作尺度与灰区可读性

代码事实：批量栏直接由 Layout + Badge + 两个 Button 构成。Badge 使用 min-height:24px、11px 字号；Button 为 36px、13px，两者没有共同组合尺寸契约。Layout 只排布，不提供这类契约。按钮之间高度相同，截图差异主要是 Badge 与按钮不同，并非 plain 自动变小。

表格：Surface 为 #f2f2f2，未选 Checkbox 与 neutral Badge 用 #ececec；表头用 muted，数据用 body，编辑动作也用 body，但主文字字重更高。行分隔已存在。灰区可读性问题需要分为控件边界、字段层级、状态识别与正文阅读，不能笼统归因于所有文字颜色过浅。

根因：逐个组件的默认尺寸被直接拼接，缺少组合内的几何节奏；表格套用了通用控件颜色，而没有完整的数据阅读与操作识别计划。某些灰色块色差很小，但暗色选中标记和动作文字很醒目，使信息权重失衡。

分类：组合规划缺失是主要问题；现有 R1/R7/R10 尚未落实。同时，规则缺少如何为密集数据建立阅读层级、如何使小型控件在承载底色中可辨认的检查标准。

待补原则：同一操作行协调视觉尺度和对齐，而非强制所有 Badge 在所有场景和 Button 一样高。数据区先定义主要数据、辅助属性、状态与操作的阅读顺序，再决定灰阶、留白、行分隔和控件边界。中性色阶有限不等于每层必须铺灰，也不等于禁止为识别增加必要边界。

## 5. 相似卡片的常驻标识与背景 hover

用户事实：另一参考卡片的左下角标识常驻，hover 改变卡片背景。截图标识带作者符号与 @ 文本；更像身份/归属信息，这一职责判断属于推断，需用户确认。

根因判断：两个卡片的外形相近，但局部信息职责、常态所需信息与反馈承担者可能不同。不能因为都称 card，就要求出现方式、底色、hover 完全相同；也不能未经区分就新增一堆任意视觉变体。

分类：这是当前规则缺少“同形结构、不同职责”的证明，不应直接视为参考站风格矛盾。仅凭这两张图也不能认定它们分别是固定的两类组件。

待补原则：分别记录常态保留什么信息、交互透露什么信息、哪些元素是独立操作、哪一层承担 hover。结构可复用，信息策略和反馈范围需按职责确定。

## 本轮尚待讨论的原则缺口

1. 信息注释、归属信息、控件与独立工具的表面职责尚未区分清楚。
2. 控件本体与字段展示绑定，无法证明组合的可复用性。
3. 描边和字重只规定参数，没有图标/文字联合的视觉重量校准。
4. 单件尺寸尺度已经存在，组合内的几何节奏和数据阅读层级尚未规划。
5. 同形结构可承担不同任务；常态信息与交互反馈的分工尚未形成明确记录。

已有的“以可读性、可用性判断”方向不因这些问题失效，但目前过于抽象，不足以稳定地产生具体设计。后续应先讨论这些缺口，再确定组件方案；本轮不据此改代码或宣称新规则已经定稿。

## 6. “当前视图 / 重置”工具栏的左右留白不平衡

依据：用户新截图与 src/spec-practice.tsx、src/app.css、src/ui/components.css。用户要求堵住规范和实践漏洞，不直接修改此实例。

源码事实：spec-tools 统一 padding 为 space-2（4px）、gap 为 space-3（6px）。其子项依次为裸 Icon、裸 span、Button。左侧图标外缘只有容器 4px 加图标绘制内距；右侧重置文案另有 Button 右 padding 14px，加容器 4px，形成 18px 的布局留白（不计字形内距）。按钮高度、内距与文字布局仍存在于 plain 变体，透明底色没有取消按钮的几何。

根因：把针对完整按钮子项的紧凑底座 inset 用到裸内容与按钮混排；外观上融为一体，几何上却没有统一组合单元。Icon 与说明没有独立的信息单元定义，容器只负责排列，未负责首尾可见边界和内容间距。规范只提出留白、对齐、共同边界，没有规定由谁承担内容边距，也没有要求评审从可见内容计算有效留白。这是规则缺项与实践选型错误共同导致的。

补齐的约束：组合分别定义容器外缘、单元内部、组内/组间及命中范围；按可见内容而非盒子核查首尾与间距；混排必须确认子项留白前提。普通说明仍是信息，不应为获得 padding 改造成按钮。小 inset 不是所有工具栏的通用默认值，plain 不是几何归零。核查覆盖不同首尾类型、尺寸和换行，不采用实例偏移补丁。

本轮只补规范、Token 消费说明与审查记录。没有修改上述代码或运行浏览器/测试。实例仍保留现状，待按新契约统一处理组合时再实施。
