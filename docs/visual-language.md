# Uagray

## 视觉语言与组件设计准则

**Visual Language & Component Design Guidelines · v0.1**

整理日期：2026-10-10。本文确立 Uagray 的视觉方向与 P01–P10 核心准则。参考观察来自用户提供的研究文稿与既有档案，不表示本轮逐条重新验证了参考网站。原稿保存在 [来源文稿](references/uagray-visual-language-v0.1-source.md)。

本文中的组件外观/API 建议与验证计划保留提案状态；实施细则见 [组件与组合契约](design-system.md)，代码现状见 [审查记录](design-audit.md)。十条准则是当前核心，不因遇到一个新组件就继续增加原则；发现明确缺口时才修订。2026-10-10 已确认 [表面实施契约](surface-contract.md)：灰底常态表面限定透明、深一级灰、白色；tone 同步适配；常驻描边仅允许白底强调对象。本文参考观察不构成对冲突样式的实施授权。

**研究基础：** anishfn 个人网站及 Lab 项目的界面实践  
**目标：** 建立一套克制、清晰、一致且具有扩展能力的视觉设计系统，能够适用于内容网站、SaaS、Dashboard、编辑器及其他数字产品。

# 01. 设计理念

### 1.1 核心理念

通过有限的视觉资源、精确的局部对比，以及清晰的内容与对象关系，建立具有高度一致性和低视觉噪声的界面。

我们将其概括为：

**Minimum Sufficient Contrast — 最小充分对比。**

这意味着，设计不应通过不断增加背景、边框、阴影来强化层级，而应当根据实际的信息结构和交互需求，选择足以建立识别的视觉手段。

**Clean 不等于简单，也不等于减少一切视觉属性，而是避免没有明确职责的视觉表达。**

一套高质量的极简界面，应该同时具备：

- **Clarity：清晰性。** 信息、对象、操作和状态能够被准确识别。
- **Consistency：一致性。** 相同职责的组件遵循可预测的视觉规则。
- **Restraint：克制性。** 避免不必要的色彩、边界与装饰。
- **Flexibility：适应性。** 能够覆盖不同信息密度和交互复杂度的场景。
- **Coherence：协调性。** 不同组件可以拥有不同外观，但始终维持统一的视觉语言。

这里需要明确一个重要区别：

**视觉语言的一致性，不等于视觉属性的完全一致。**

两个组件不需要使用相同的背景、描边或阴影，才能属于同一套设计系统。

我们真正追求的是设计决策的一致性。

### 1.2 研究结论的可靠性

本规范基于实际界面截图与交互观察。

需要区分两个层面：

**Reference Observations（参考观察）**

能够直接从参考作品中确认的视觉关系、组件结构和交互表现。

**Uagray Design Decisions（系统决策）**

为了让视觉语言具备可扩展性和可复用性，由我们主动制定的规范。

两者不能混淆。

特别是，参考作者在不同页面中使用过多种不同的 Input 样式、描边方式和阴影处理。

因此，我们不能假定作者拥有一套完整、严格且始终一致的设计系统。

**Uagray 的任务不是还原作者可能存在的内部规范，而是以这些实践为依据，建立属于自己的可靠规则。**

# 02. 视觉层级模型

这是整个系统最重要的基础。

我们决定不采用单纯按照颜色深浅建立的层级体系。

例如：

`White → Light Gray → Gray → Dark`

不能直接等同于：

`Level 0 → Level 1 → Level 2 → Level 3`

因为颜色和空间关系并不总是对应。

### 2.1 三种独立的层级

| 层级                  | 定义                             | 主要表达方式                   |
| --------------------- | -------------------------------- | ------------------------------ |
| Information Hierarchy | 信息的重要程度及从属关系         | 排版、字号、字重、间距、对比度 |
| Object Hierarchy      | 哪些元素构成整体，哪些是独立对象 | 分组、Surface、边界、间距      |
| Spatial Hierarchy     | 元素之间真实的前后叠放关系       | Overlay、遮挡、阴影、定位      |

三者之间可以存在联系，但不能互相替代。

**案例 A：Guestbook**

灰色容器中包含多个白色留言卡片。

这里表达的是对象层级：

- 灰色容器：留言集合。
- 白色卡片：独立留言。
- 卡片内部：留言内容。

白色卡片不一定具有更高的空间层级。

**案例 B：Segmented Control**

灰色轨道中包含独立的白色选中滑块。

滑块表达选中状态，并不意味着它是独立的浮动窗口。

**案例 C：Jump to 搜索框**

白色搜索框具有描边和明显阴影，并且浮动在页面内容之上。

这里才存在明确的空间叠放关系。

**设计准则 P01**

> 不使用单一的颜色等级表达全部层级。应当首先判断需要表达的是信息关系、对象关系还是空间关系，再选择对应的视觉手段。

# 03. Surface System：表面体系

## 3.1 基础表面

根据参考作品，我们确定四种主要的表面资源。

| 名称  | 视觉特征           | 主要职责                           |
| ----- | ------------------ | ---------------------------------- |
| Base  | 接近白色的全局背景 | 建立连续的基础视觉环境             |
| Muted | 低对比度浅灰色     | 建立区域、对象和控件之间的柔和区分 |
| White | 白色               | 在局部环境中建立清晰的表面对比     |
| Dark  | 接近黑色           | 提供高对比度的视觉强调             |

另有一种重要表现：

**Transparent：不创建独立背景。**

它并不是另一种实体材质，而是允许内容直接使用当前环境的表面。

### 3.2 Base 是默认环境

在参考案例中，我们观察到一个非常稳定的特征：

**已观察的参考页面采用接近白色的 Base，而不是以纯白色作为大面积的页面背景。**

普通内容通常直接排列在 Base 上。

例如：

- 页面标题、正文和辅助信息。
- Breadcrumb。
- 普通链接。
- 部分 Ghost Button。
- 不需要独立视觉边界的信息分组。

**设计准则 P02**

> Base 是默认的连续工作环境。结构分区不自动意味着需要创建新的背景表面。

例如在 SaaS 中：

Sidebar、Main Content 和 Inspector 可以共享 Base。

它们可以通过分割线、间距和排版区分，而不需要每个区域分别使用不同颜色。

这将是避免复杂界面过度 Card 化的重要基础。

---

## 3.3 Muted 是最主要的局部表面

Muted 的用途非常广泛。

根据参考案例，至少包括：

| 用途         | 实际案例                        |
| ------------ | ------------------------------- |
| 展示区域     | Lab 项目的 Preview              |
| 内容集合     | Guestbook 主页模块              |
| 独立内容对象 | Guestbook 独立页面的留言卡片    |
| 交互控件     | Search Input、普通 Button       |
| 组合控件背景 | Segmented Control、Button Group |
| 文本体例     | Code Block、Inline Code         |
| 临时交互反馈 | Breadcrumb Hover、Button Hover  |
| 内部功能区域 | White Composer 中的输入区域     |

这说明：

**Muted 本身不具有固定的组件语义。**

它不是 Card 专属的颜色。

也不是 Button 专属的颜色。

更不是比 Base 更高或更低一级的空间层级。

它是一种低对比度的表面资源。

其实际职责取决于使用它的对象。

**设计准则 P03**

> 优先使用 Muted 在 Base 上建立轻量、明确的局部区分，但不将 Muted 与任何特定的组件类型或交互状态绑定。

---

## 3.4 White 是局部对比表面

White 是我们研究中争议最多的部分。

经过多个案例验证，现在可以比较明确地得出：

**White 不一定具有描边，也不一定具有阴影，更不天然代表 Raised。**

例如：

**Guestbook 主页**

`Base → Muted Collection → White Items`

白色留言卡片没有明显描边和阴影。

仅依靠色差，就建立了足够清晰的对象边界。

**Segmented Control**

`Base → Muted Track → White Indicator`

白色滑块具有额外的边缘处理。

这是为了强化其选中指示器的轮廓和视觉特征。

**Jump to**

白色的全局搜索组件可以覆盖不同的背景，使用描边和更明显的阴影。

其主要目的之一，是维持浮动对象的独立性和识别度。

因此，我们不能将 White 直接定义为一种固定的组件等级。

**设计准则 P04**

> White 是一种可用于建立局部表面对比的材质。是否添加描边与阴影，应由对象的边界需求、视觉特征及空间关系独立决定。

---

## 3.5 Surface 不是严格的嵌套阶梯

参考作品中存在以下关系：

| 组合                | 示例                            |
| ------------------- | ------------------------------- |
| Base → Transparent  | 普通正文、Ghost Button          |
| Base → Muted        | Code Block、独立 Guestbook Item |
| Base → White        | 浮动 Jump to                    |
| Muted → Transparent | Table Row、普通文本             |
| Muted → White       | Guestbook Item、Composer        |
| Muted → Dark        | 主要操作、激活工具              |
| White → Muted       | Composer Input、快捷键标识      |
| White → Transparent | Toolbar 内部普通按钮            |

这里需要避免一种机械规则：

`Base → Muted → White → Muted → White...`

我们并不希望组件随着嵌套深度不断交替颜色。

**每次创建新表面，都必须重新判断其必要性。**

# 04. Boundary System：边界体系

表面负责提供色彩差异。

边界则负责强化对象的视觉轮廓。

两者相关，但必须分离。

## 4.1 三种主要的边界表达

| 模式     | 主要手段             | 视觉特征               |
| -------- | -------------------- | ---------------------- |
| Tonal    | 背景色差             | 轻量、柔和、无额外轮廓 |
| Defined  | 背景与描边           | 轮廓明确，实体感较弱   |
| Physical | 背景、边缘及适量阴影 | 具有更明显的实体质感   |

这些是视觉处理模式，而非空间层级。

它们不构成严格的强弱顺序。

### Tonal：通过表面对比建立边界

**案例：Guestbook**

Muted 容器中的 White Item。

它们没有明显边框或阴影。

但对象边界仍然非常清晰。

这证明：

**不需要给每个独立对象提供完整的 Stroke 和 Shadow。**

### Defined：通过描边强化轮廓

**案例：Guestbook Modal**

输入框使用白色背景和浅灰色描边。

在 White Modal 内，白色填充无法提供足够的色差，因此通过边框建立输入区域。

**案例：404 页面**

参考记录中的 Muted Button 存在 Border，这仅是参考观察。Uagray 当前不采用该模式：常驻对象描边仅允许白底强调对象。

### Physical：使用轻微实体质感

**案例：Segmented Control 滑块**

White + Border + 微阴影。

**案例：Keyboard Shortcut**

使用类似实体键帽的视觉表达。

**案例：Jump to**

具有更加明确的边框与阴影。

这里的阴影同时参与了浮动关系的表达。

### 4.2 边界设计的基本原则

**设计准则 P05**

> Fill、Border 和 Shadow 应作为独立的视觉资源管理，并优先使用能够满足识别要求的最少组合。

实践中的优先判断是：

1. 是否可以不创建背景？
2. 背景色差是否足够？
3. 是否需要额外描边？
4. 是否确实需要阴影或更明显的实体质感？

注意，这不是要求所有组件必须逐级升级。

例如某些 Focus 状态即使没有背景，也可能直接需要明显轮廓。

而某些物理隐喻明确的控件，也可以在已经足够清晰的情况下保留微阴影。

我们要约束的是无意义的装饰叠加，而不是禁止合理的设计表达。

# 05. Composition：组件与容器的组织原则

这是避免 SaaS 界面失控的关键。

## 5.1 区分 Continuous 与 Discrete

### Continuous Content

连续型内容。

例如：

- Table
- List
- Property Group
- Settings
- Form Section

多个内容单元共同构成连续的信息结构。

此时，应优先让它们共享一个表面。

内部使用排版、间距和分割线建立区分。

**参考案例：灰色信息表格。**

整个表格使用 Muted。

内部每一行都直接排列在同一个表面上。

不需要为每行增加独立卡片。

### Discrete Content

离散型内容。

例如：

- Gallery Item
- Guestbook Item
- Project Card
- 独立预览对象

这些内容需要被识别为彼此独立的视觉对象。

因此，它们可以各自拥有背景。

**参考案例：Guestbook。**

主页：

`Muted Collection → White Items`

独立页面：

`Base → Muted Items`

同一种内容在不同组织环境中使用不同表面，但维持了相近的对象识别方式。

**设计准则 P06**

> 连续内容优先共享表面；离散对象可以通过独立表面建立边界。是否创建背景由内容组织关系决定，而不是由组件名称决定。

需要特别说明：

Continuous 和 Discrete 是布局组织策略，而非数据类型。

同一组数据可以采用连续列表，也可以采用独立卡片。

但两种组织形式应当分别具有明确且一致的视觉规则。

---

## 5.2 避免重复的视觉边界

参考作品中的 Button Group 是一个很好的例子。

它具有完整的 Muted 外壳。

内部按钮默认透明。

Hover 时，当前按钮才出现更深的灰色背景。

这说明：

**当父级已经承担了完整控制对象的边界时，子级不一定需要再次绘制永久可见的背景。**

类似规则还可以应用于：

- Toolbar
- Menu
- Navigation Group
- Button Group
- Segmented Control

但这不意味着内部不允许出现新表面。

例如 Segmented Control 中的 White Indicator。

外层边界表达整个控件。

内层滑块表达当前选择。

两者职责不同，因此可以共存。

**设计准则 P07**

> 视觉边界应由最适合表达对象关系的层级承担。允许不同职责的边界嵌套，但避免父子组件重复承担相同的边界职责。

这条原则可以理解为 **Boundary Ownership（边界归属）**。

# 06. Interaction：交互状态与视觉反馈

我们不应该为所有组件规定完全相同的 Hover、Focus 或 Selected 外观。

因为交互模型不同。

## 6.1 Segmented Control 与 Button Group

这是最有力的参考案例之一。

| 属性         | Segmented Control        | Button Group             |
| ------------ | ------------------------ | ------------------------ |
| 外层         | Muted                    | Muted                    |
| 内部默认     | Transparent              | Transparent              |
| Hover        | 未选中项主要改变文字颜色 | 当前按钮出现更深灰色背景 |
| 持续选择状态 | 独立 White Indicator     | 不一定存在               |
| 交互模型     | 单选                     | 独立操作集合             |

这两种组件虽然外观接近，但交互机制不同。

Segmented Control 使用独立滑块表达持续选择。

因此，未选中项 Hover 的视觉强度受到控制，以避免与滑块竞争。

Button Group 不存在同样的选择指示器，因此可以通过局部填充强化 Hover 目标。

**设计准则 P08**

> 交互反馈必须服从组件的交互模型。相同的交互状态名称，不意味着所有组件都必须采用相同的颜色或背景变化。

---

## 6.2 区分三种状态表达

| 状态类型           | 作用                 | 常见表现                       |
| ------------------ | -------------------- | ------------------------------ |
| Resting Appearance | 定义组件默认如何存在 | Transparent、Muted、White      |
| Transient Feedback | 响应短暂交互         | Hover、Pressed、Focus          |
| Persistent State   | 表达持续状态         | Selected、Checked、Tool Active |

这三个层面需要分别设计。

例如：

- Ghost Button 可以默认透明，Hover 时出现 Muted。
- Search Input 可以默认 Muted，Focus 时增加明显轮廓。
- Segmented Control 可以保持 Muted Track，通过独立的 White Indicator 表达 Selected。
- Toolbar 中的当前工具可以使用 Dark 表达激活状态。

不能因为它们都属于「交互反馈」，就要求它们使用同一种背景变化。

### 无背景不意味着没有交互性

Ghost Button 是一种正常的交互组件。

但必须确保其可操作性能够被用户理解。

同时，Focus 需要为键盘用户提供清晰可见的反馈。

对于只在 Hover 时显示的操作，还需要考虑键盘与触屏场景。

# 07. Emphasis：视觉强调

## 7.1 Dark 是强调资源，而不是空间层级

参考作品中，Dark 主要出现在：

- Guestbook 的 Sign it。
- 编辑器中的 Make it 3D。
- 当前激活的 Brush 工具。
- 其他需要明确强调的操作。

这些对象并不都具有相同语义。

Sign it 是主要操作。

Brush 是当前工具。

但它们都需要在局部环境中获得较高的视觉显著性。

因此：

**Dark 不等于 Primary，也不等于 Selected，更不等于 Raised。**

它是一种高对比度强调资源。

**设计准则 P09**

> 高对比度视觉资源应优先分配给具有明确操作优先级或持续状态识别需求的对象，避免无差别使用。

我们将其称为 **Controlled Emphasis（受控强调）**。

它不意味着每个页面只能存在一个 Dark Button。

但在同一组具有明确优先级的操作中，不应让所有按钮都获得同等强烈的视觉强调。

否则便失去了层级。

# 08. Component Appearance：组件外观规范

现在需要从视觉原则进入组件设计。

这里我们决定采用：

**有限的外观模式，而非完全自由的视觉属性组合。**

## 8.1 Button

建议第一阶段比较以下外观。它们是待验证的接口方向，并非本轮新增 API 的授权；当前 plain / soft / white / dark / danger 接口保持不变。

| Appearance | 主要特征     | 使用条件                                          |
| ---------- | ------------ | ------------------------------------------------- |
| Ghost      | 无常驻填充   | 轻量操作、导航、内部控制                          |
| Soft       | 低对比度填充 | 常规独立操作                                      |
| Outline    | 主要依赖描边 | 旧提案已撤销：透明/灰底常驻描边不符合当前硬性规则 |
| Solid      | 高对比度填充 | 主要操作及高强调状态                              |

需要明确：

这些是建议的组件外观 API，而不是参考作者原本的分类。

### 环境适配的默认建议

| 环境  | Ghost       | Soft                   | Solid |
| ----- | ----------- | ---------------------- | ----- |
| Base  | Transparent | Muted                  | Dark  |
| Muted | Transparent | 按职责选择独立对比表面 | Dark  |
| White | Transparent | Muted                  | Dark  |

这张表不是强制的颜色映射。

尤其在 Muted 环境下，我们不应自动将所有 Soft Button 变成 White。

还需要判断它是否真的需要持续的独立轮廓，以及是否已经由父级控制组承担边界。

透明或灰底 Outline 不再属于可实施外观。白底强调对象是否需要描边，仍须单独说明识别或分离职责。

---

## 8.2 TextField

建议提供两种受控外观。

### Filled

以 Muted 表面表达输入区域。

参考 Contact Modal。

适合希望以低对比度色块建立输入边界的场景。

### Outlined

通过描边建立输入区域。

参考 Guestbook Modal。

适合希望保持背景连续性，或需要更明确输入轮廓的场景。

**重要结论：Filled 与 Outlined 不是视觉强弱等级。**

Filled 主要依赖面积差异。

Outlined 主要依赖轮廓差异。

两者都可能显得轻量，也都可能在高密度场景中造成噪声。

### Uagray 的初步选择

Filled 为当前默认建议；Outlined 仅可在白底且具有明确强调或分离职责时讨论，透明/灰底常驻描边不再作为受控扩展。

但这属于我们的系统决策，不是已经由参考案例证明的通用规律。

还需要通过复杂表单进行验证。

同一表单中承担相同职责的字段，应优先保持外观一致。

只有在交互模型或功能职责明显不同的情况下，才考虑混用。

---

## 8.3 Card 与 Container

不建议让 Card 简单复制 Button 的 Appearance 体系。

因为 Card 首先是内容与对象的容器。

建议重点规范：

- 它是否拥有独立背景。
- 它与父级表面的关系。
- 它表达连续内容还是离散对象。
- 它是否具有交互行为。
- 它是否确实需要额外边界。

例如：

**Base 中的独立 Card：** 可以优先采用 Muted。

**Muted Collection 中的离散 Card：** 可以采用 White。

**连续信息列表：** 可以只使用一个父级 Muted 表面，而不为每条内容创建 Card。

但这些都应作为经过验证的组合模式，而不是 Card 内置的绝对颜色规则。

---

## 8.4 组合组件

对于 Toolbar、Button Group、Segmented Control 等组件，不能简单地将多个标准 Button 拼接在一起。

应当独立规定：

- 外部容器高度。
- 内部控件尺寸。
- 内部边距。
- 实际可点击区域。
- 默认和交互状态。
- 是否存在独立的状态指示器。

**参考案例：Button Group。**

整体高度可以与独立 Button 对齐，但内部按钮的视觉尺寸更小。

**参考案例：Segmented Control。**

White Selection Indicator 是独立的视觉层，而非简单地为选中 Item 设置背景。

这些结构性差异应当进入组件规范，而不是被视为单纯的 CSS 修饰。

---

# 09. 如何扩展参考作品没有覆盖的设计实践？

这是 Uagray 作为真正设计系统必须具备的能力。

我们不应该把参考作品中的组件形式视为完整的合法范围。

新外观须先满足当前硬性边界：透明或灰底的常驻 Outline 已排除，不能仅因常见组件库支持而引入。

因此，我们制定以下扩展标准。

| 评价维度       | 需要回答的问题                     |
| -------------- | ---------------------------------- |
| Necessity      | 现有模式是否真的不能合理解决需求？ |
| Consistency    | 是否符合现有视觉语言？             |
| Composability  | 与其他组件组合时是否仍然协调？     |
| Predictability | 是否具有明确的使用条件？           |
| Accessibility  | 是否保持足够的识别度和可操作性？   |
| Complexity     | 引入的额外设计与维护成本是否合理？ |

### 原 Outline Button 扩展讨论（已撤销）

以下保留早期推演，不能作为当前实施授权。透明/灰底常驻描边已经被硬性规则排除。

假设一个高信息密度的管理界面中，多个操作需要持续可识别的点击边界，但 Muted Fill 又造成了大量灰色色块。

此时，Outline 可能提供新的解决思路：

通过轻量描边保留对象轮廓，同时避免额外的填充面积。

但我们必须进行实际比较。

因为在高密度布局中，大量 Outline 同样可能造成线框噪声。

所以，新增模式必须同时解决实际问题，并保持原有视觉语言的克制程度。

**设计准则 P10**

> 设计系统允许有限扩展，但每一种新增外观都必须具有明确的使用理由、规范边界和跨场景验证结果。

---

# 10. 设计系统的架构建议

基于以上研究，我建议 Uagray 采用四层规范结构。

| 层次                     | 内容                                               | 目标                       |
| ------------------------ | -------------------------------------------------- | -------------------------- |
| Foundation               | Color、Typography、Radius、Spacing、Border、Shadow | 统一底层视觉资源           |
| Visual Patterns          | Ghost、Soft、Outlined、Solid、Tonal、Defined 等    | 沉淀重复出现的视觉处理方式 |
| Component Specifications | Button、Input、Select、Card、Toolbar 等            | 约束组件合法外观与行为     |
| Composition Guidelines   | Form、Table、Navigation、Inspector、Workspace 等   | 规范组件之间的组织方式     |

这里需要强调：

**Visual Patterns 首先是一层设计规范，不一定需要成为独立的代码或 Token 层。**

只有当某种处理方式在多个组件中表现出稳定的复用价值时，才有必要将其提升为共享实现。

同样，我们不应该让组件库使用者任意组合所有 Foundation 属性。

例如：

```tsx
<Button surface="white" border="strong" shadow="large" />
```

即使底层技术允许，也不意味着应该成为推荐的组件 API。

更合理的是通过经过验证的 Appearance，提供有限且语义清晰的选择。

从而保持组件库的可预测性。

# 11. 复杂页面的实践准则

前面的规则最终必须能够用于真实产品。

我们仍然以 Typography Tokens 管理控制台作为未来的验证场景。

建议遵循以下决策顺序。

### Step 1 — Structure

首先确定页面的信息结构。

明确哪些是并列区域、哪些是连续内容、哪些是独立对象。

**不预先为每个结构区域赋予背景。**

### Step 2 — Base

将 Base 作为默认环境。

优先利用排版、间距和必要的分割线完成初步组织。

### Step 3 — Surface

判断哪些内容真正需要独立表面。

能够直接排列的，不必创建背景。

需要柔和区域区分的，优先考虑 Muted。

需要局部独立对象的，再考虑与周围环境形成对比的表面。

### Step 4 — Boundary

判断色差是否已足够建立边界。

只有在必要时，才增加描边和阴影。

### Step 5 — Emphasis

明确主要操作和需要持续强调的状态。

有意识地分配 Dark 等高对比度资源。

### Step 6 — Interaction

分别检验：

Default、Hover、Focus、Pressed、Selected、Disabled。

不能只根据静态截图判断组件是否符合规范。

### Step 7 — Composition

最后必须整体观察。

重点检查：

- 是否出现了大量没有明确职责的背景块。
- 是否存在重复的父子边界。
- 高对比度元素是否过多。
- 同类操作是否出现缺乏理由的样式差异。
- 信息密度提高后，视觉关系是否仍然清晰。

**局部组件的正确，不意味着整体页面必然正确。**

这是整个研究中值得反复强调的结论。

# 12. 哪些结论已经可靠，哪些仍需验证？

为了避免今后陷入反复修改规则的情况，我建议明确区分两类结论。

### A. 已有较充分案例支撑的原则

| 结论                                      | 可靠性 |
| ----------------------------------------- | ------ |
| Base 是默认的连续页面环境                 | 高     |
| Muted 不对应固定的组件语义或空间层级      | 高     |
| White 不必绑定 Border 与 Shadow           | 高     |
| 相同内容对象可根据组织环境使用不同表面    | 高     |
| 表面颜色与空间层级应分离                  | 高     |
| 连续内容与离散内容需要不同组织策略        | 高     |
| Hover、Selected、Focus 应服从组件交互模型 | 高     |
| 父子组件不必都拥有常驻的独立背景          | 高     |
| Dark 在参考作品中被克制地用于强调         | 高     |

这里的「高」是指现有截图对这些判断具有较强支持，不代表已经在所有产品场景中得到验证。

### B. Uagray 主动提出、仍需验证的规范

| 决策                                | 当前状态                                             |
| ----------------------------------- | ---------------------------------------------------- |
| Filled Input 作为默认样式           | 待复杂表单验证                                       |
| 透明/灰底 Outline Button            | 已排除：不符合常驻描边硬性规则                       |
| Button 使用 Ghost / Soft / Solid    | 待组件验证                                           |
| Surface Context 影响组件默认外观    | 待跨环境验证                                         |
| 统一的 Border 与 Shadow Token 体系  | 待细节实验                                           |
| SaaS 中 Table、Inspector 的表面组织 | 待完整页面验证                                       |
| 深色模式中的表面与强调规则          | 已有主题与语义色实现；尚未完成跨场景视觉及可用性验证 |

我认为这里尤其要避免一个错误：

**不能因为某个规则很好地解释了参考作品，就直接认为它已经能够适用于 Uagray 的全部场景。**

设计准则需要具有解释能力。

组件规范还必须具有预测能力。

两者缺一不可。

# 13. 最终设计准则总览

最后，我把我们这次讨论真正值得保留的原则整理成一张总表。

这十条可以作为 Uagray 第一版视觉设计规范的核心。

| ID  | Principle                       | 设计要求                                                 |
| --- | ------------------------------- | -------------------------------------------------------- |
| P01 | **Independent Hierarchies**     | 区分信息、对象与空间层级，不使用单一色阶表达全部关系     |
| P02 | **Base Continuity**             | Base 是默认连续环境，不为所有结构分区自动创建背景        |
| P03 | **Contextual Surface**          | 表面材质依据对象职责和视觉环境使用，不绑定固定组件语义   |
| P04 | **Surface–Edge Independence**   | Surface、Border 与 Shadow 分离，不默认绑定               |
| P05 | **Minimum Sufficient Contrast** | 优先使用足够完成识别任务的最少视觉属性                   |
| P06 | **Meaningful Containment**      | 根据连续与离散的内容关系建立视觉容器                     |
| P07 | **Boundary Ownership**          | 边界由具有明确表达职责的层级承担，避免无意义的重复       |
| P08 | **Semantic Interaction**        | 交互反馈服从组件模型，不强求所有组件使用相同状态外观     |
| P09 | **Controlled Emphasis**         | 克制地分配高对比度强调资源，维持清晰的视觉优先级         |
| P10 | **Constrained Extensibility**   | 允许有限的新视觉模式，但必须经过必要性、一致性及组合验证 |

其中，我认为最能体现 Uagray 设计哲学的是三个原则。

**P05 — Minimum Sufficient Contrast**

它决定整个系统如何建立视觉层级。

**P07 — Boundary Ownership**

它决定组件与容器如何组织，以及为什么某些控件需要独立背景、某些不需要。

**P10 — Constrained Extensibility**

它决定 Uagray 如何超越参考作品，同时不失去自身的视觉一致性。

这三条分别回答：

**如何表达、如何组合、如何扩展。**

---

# 14. 最终结论

经过这轮研究，我认为我们已经形成了一个相对可靠的设计方向。

首先，我们不应该将参考作品理解为一套完全严格的组件体系。它存在相当多的局部设计选择，甚至在相似组件之间也存在明显的表现差异。

但是，它所呈现出的视觉语言具有稳定的共同特征。

这些特征并不只是大圆角、浅灰色或轻阴影。

更重要的是：

**以 Base 建立连续的视觉环境，以 Muted 进行柔和的区域与对象区分，以 White 建立必要的局部对比，以 Dark 提供克制的强调，并通过排版、边界和交互反馈组织完整的视觉关系。**

这套设计能够表现出很高的 Clean 感，关键并不是避免复杂性，而是使复杂性有序存在。

因此，Uagray 不应该追求所有组件都使用相同的颜色、描边和阴影。

它应该追求：

**相同的视觉原则、明确的组件职责、有限的合法外观，以及可预测的组合方式。**

最后，我想为这份规范确定一句核心表述：

> **Uagray is a restrained visual system that establishes clarity through contextual contrast, meaningful boundaries, and consistent interaction.**
>
> Uagray 是一套克制的视觉系统，通过适当的上下文对比、有意义的边界和一致的交互，建立清晰的视觉秩序。

这可以作为 Uagray 设计语言的第一版正式方向。

**目前不必继续增加原则了。** 十条准则已经足够支撑下一阶段的设计工作。接下来遇到新的组件或场景时，我们应该优先检验现有准则是否能够解释并指导设计；只有发现明确的不足，才考虑修订规范。

这样，这套系统才会随着实践逐渐成熟，而不是随着组件数量增长，不断增加相互矛盾的规则。
